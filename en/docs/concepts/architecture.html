Performance and internals

Technical architecture

How the graph runtime, drawing layers, scheduling, layouts, and interactions work together

View source on GitHub

This page explains module responsibilities and collaboration for readers exploring rendering, performance paths, or extension boundaries. See Graph lifecycle methods for the application calling sequence.

Architecture layers

Applications use Graph and extension contracts from the package root. Graph orchestrates transforms, layouts, and the runtime; DataModel owns graph data and states; RenderScheduler coordinates drawing based on the scope of each change. Renderer, Picking, and GPU buffers are internal implementation details.

These layers share one graph runtime. Layouts provide positions, interactions produce data or state changes, and the scheduler sends changes to the appropriate drawing layers. This division lets layouts, information layers, and interactions be extended independently.

Drawing layers

G6Lite batches nodes and edges through WebGL and uses Canvas 2D for text measurement, label collision, and grouping bounds:

Layer, bottom to topContentReason
Canvas 2D underlayCombo boundariesFits group bounds and background information
Main WebGL canvasNodes, edges, and arrowsSupports batched geometry and buffer updates
Canvas 2D overlayLabels, icons, and decorationsSupports text measurement, layout, and collision handling

The layers share the camera, dimensions, DPR, and scheduling signals within one Graph. WebGL prefers WebGL2 and falls back to WebGL1. See Browsers and runtime for environment requirements.

Rendering and update paths

First-render data flow

Calling render() prepares input, builds the runtime, and draws the first frame:

After asynchronous layout, Graph checks generation and destruction before committing stale results. The render Promise describes initialization/submission, not GPU completion; consult the lifecycle contract for plugin mounting and other boundaries. Generations are an internal cancellation and result-commit mechanism; applications manage instances through public lifecycle methods.

Frequent-update paths

RenderScheduler selects processing based on the change level:

ChangeMain path
Node selected / highlight / inactiveResolve state and patch GPU styles, reprocessing when required
Edge business fields or statesFully process data to keep edge types, visibility, and arrow batches aligned
Batched node positionsUpdate adjacency data, upload affected buffer ranges, redraw Canvas layers
Label or Combo informationRedraw the corresponding Canvas 2D information layer
Camera pan and zoomUpdate uniforms and draw without rebuilding graph-data buffers
Full replacement or structural changeUpdate DataModel and fully or partially process render data and buffers

Selection, highlighting, and dragging should update the existing instance through state, position, and batch APIs. See Data for choosing update methods and Performance tuning for practical guidance.

Layout and interaction collaboration

Layout and Worker

The layout layer computes positions from graph data and configuration. Graph commits the result to DataModel and passes it to Renderer. Official algorithms are lazy-loaded by layout.type; supported expensive layouts can run in a Worker to reduce main-thread blocking.

Cancelled layout results are not committed to the active render generation. A Worker does not remove algorithm cost, and data with existing coordinates can omit layout. See Layout configuration for algorithms, options, and Worker limits.

Interaction and picking

InteractionDispatcher centralizes pointer events and hit detection, then delivers normalized events to Behaviors:

Nodes and edges prefer GPU Picking and fall back to CPU detection when the picking buffer is unavailable. Combo uses its own geometric hit path. Picking buffers are maintained on demand; drawing does not always require a picking pass.

Interaction changes return through the update scheduler, so Behaviors do not need to manipulate framebuffers. See Interactions and Events for application usage.

Extension boundary

G6Lite supports node, edge, label, decoration, layout, behavior, transform, and plugin extensions. These contribute shape descriptions, information layers, positions, event responses, or runtime orchestration.

Stateful extensions collaborate through the data, state, viewport, and requestRender() capabilities of ExtensionContext. They should not hold internal DataModel, Renderer, WebGL contexts, or GPU buffers.

See Extensions for registration, instance scope, and cleanup. See the Extension API for signatures and types.
