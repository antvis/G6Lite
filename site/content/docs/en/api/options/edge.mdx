`GraphOptions.edge` has type `EdgeConfig`. This page covers basic appearance, arrows, picking width, states, and runtime updates. Follow the [edge guide](/en/docs/guides/edge) for steps; existing curve, routing, label, and parallel-edge references are under [Other configuration](#other-configuration).

## EdgeConfig

All top-level fields are optional.

| Field | Type | Default behavior and entry |
| --- | --- | --- |
| `type` | `'line' \| 'arc' \| 'polyline' \| 'cubic' \| string` | Defaults to `'line'`; register custom names with `register('edge', ...)`, using the extension's declared `base` |
| `style` | `EdgeConfig['style']` | Appearance field object; callback-capable fields use `EdgeStyleValue<T>` below |
| `stateStyles` | `Partial<Record<EdgeState, EdgeStateStyleOverride>>` | Override appearance per state; see [State styles](#state-styles) |
| `labelRenderer` | `string` | Default edge-label renderer when omitted; register a named label extension first and supply nonempty `edge.style.label` |
| `parallelEdges` | `boolean \| ParallelEdgesConfig` | Omission does not enable separation through this field; an existing transform entry still operates independently. See [Parallel edges](/en/docs/guides/parallel-edges) |

Built-in types represent straight lines, arcs, polylines, and cubic Bézier curves. Unknown names currently fall back to a line primitive; do not rely on that instead of registration. See [`GraphEdge`](/en/docs/api/options#edge-graphedge) for `source`, `target`, and `id` data fields.

## Basic styles

These fields belong in `edge.style`. Defaults apply to built-in edges; themes and edge extensions can alter fallbacks.

| Field | Type | Default or fallback | Meaning |
| --- | --- | --- | --- |
| `stroke` | `EdgeStyleValue<string>` | `theme.edgeStroke`; light `'#99ADD1'`, dark `'#637088'` | Edge and arrow color |
| `lineWidth` | `EdgeStyleValue<number>` | `theme.edgeLineWidth`, preset `1` | Visual width; use a finite positive value |
| `opacity` | `EdgeStyleValue<number>` | `1` | Opacity from `0` to `1` |
| `lineDash` | `EdgeStyleValue<number[]>` | `[]` | Empty means solid; the current period uses the sum of the first two values, as described in [Dash rules](#dash-rules) |
| `startArrow` | `EdgeStyleValue<boolean>` | `false` | Source-end arrow pointing toward `source` |
| `endArrow` | `EdgeStyleValue<boolean>` | `theme.edgeArrow`, `true` in both light and dark | Target-end arrow pointing toward `target` |
| `arrowSize` | `EdgeStyleValue<number>` | Derived from line width | Length along the path; use a finite positive explicit length. Nonpositive values use automatic length |
| `hitAreaWidth` | `EdgeStyleValue<number>` | Final `lineWidth` | Total picking width, independent of visual width; see [Picking width](#picking-width) |

`lineWidth`, `hitAreaWidth`, `arrowSize`, and dash periods use screen-rendering pixels and retain their rendered dimensions across camera zoom. Do not multiply them by zoom, DPR, or picking framebuffer scale. Node positions remain in graph coordinates.

The three rows are Plain (thin gray solid line, no arrows), Dash (translucent orange dashes, target arrow), and Both (thick blue solid line, arrows at both ends). All arrows explicitly use `arrowSize: 16`. Click an edge for its purple selected style; reset restores the initial effect.

### Style callbacks

`EdgeStyleValue<T>` is `T | ((source: GraphNode, target: GraphNode, edge: GraphEdge) => T)`. The first two arguments are endpoint nodes; the third is the edge. Read edge business fields from `edge.data`. The example maps color, width, dashes, opacity, and arrow directions.

The public `style` type is a field object, not a function returning the whole object. Per-field precedence is explicit edge style → extension `getStyle(source, target, edge)` result → extension default style → theme or built-in fallback. Keep callbacks inexpensive and provide valid fallbacks for missing data.

### Dash rules

The renderer uses `lineDash[0] + lineDash[1]` as the period, drawing half and leaving half empty; later entries are ignored. Thus `[4, 12]` and `[8, 8]` look the same, rather than following arbitrary Canvas dash sequences. Fewer than two entries or a nonpositive period produces no dashes. Use finite nonnegative values with a positive sum.

Built-in straight lines can use a 1-pixel rendering path when no wider geometry or state requirement is present; that path does not draw dashes. For predictable dashed lines, explicitly set `lineWidth > 1`, as above. Dash gaps remain pickable; arrowheads are not interrupted by the dash period.

## Arrows

`startArrow` and `endArrow` control the source and target ends defined by edge data. Explicitly set `endArrow: false` to disable the preset target arrow.

Automatic length is `10` for width at most `2`, `12` for width above `2` and at most `4`, and `Math.round(lineWidth * 2.5)` for thicker lines. `arrowSize` controls length along the edge; transverse width is line width plus `12`, rather than both dimensions being set together. Arrows meet the endpoint node boundary, with space reserved in the line body.

The current static path caches automatic length from the base width. When a state changes width, static and per-field callback paths can produce different automatic arrow lengths. Specify a positive `arrowSize`, such as `16` above, when you need a predictable size across states.

## Picking width

`hitAreaWidth` is the total hit width around a path. For example, `24` gives approximately `12` on each side; the hit area itself is invisible. After resolution it is at least the visual width. Negative, non-finite, or omitted values fall back to visual width.

Both edges below have visual `lineWidth: 1.5`. The upper hit width is `2`; the lower is `24`. Click near the thin lines: the lower one is easier to select. Selection changes color to purple while keeping the thin visual width. Zoom with the toolbar and compare again; picking width retains its screen-rendering size semantics.

Hover, click selection, tooltips, and edge dragging share the picking result. Configuring hit width alone does not install a behavior; the example uses `click-select`. Lines, arcs, curves, polylines, self-loops, and arrowheads use this policy. Compare more paths in the [thin-edge example](/en/docs/examples/edge-hit-area).

## State styles

`EdgeStateStyleOverride` accepts the following constants, not field callbacks:

| Field | Type | Effect |
| --- | --- | --- |
| `stroke` | `string` | Override edge and arrow color |
| `lineWidth` | `number` | Override visual width |
| `hitAreaWidth` | `number` | Override total picking width, never below the current visual width |
| `opacity` | `number` | Override opacity |
| `lineDash` | `number[]` | Override dash-period input |

Activate states through behaviors or `graph.setItemState(edgeId, state, value)`. Each state chooses the first defined object from configuration, extension, and theme; it does not merge fields with the same theme state. States apply in state-set iteration order, later fields winning; `default` is skipped. `hidden` takes priority and sets resolved opacity to `0`. See [Graph state and visibility APIs](/en/docs/api/graph#state-visibility-and-focus).

## Runtime updates

After the first `await graph.render()`, call `graph.updateOptions({ edge: { style: ... } })` on the existing instance. Style fields merge, while a supplied `stateStyles` replaces the entire state map; submit a complete map to retain other states. This recomputes appearance without rerunning layout. Update business fields with `updateEdgeData()`; update endpoints through its batch form, supplying `id`, `source`, and `target` in each update item. See [Edge mutations](/en/docs/api/graph#edges) and [`updateOptions()`](/en/docs/api/graph#updateoptions).
