本页解释 G6Lite 各模块的职责及协作方式，适合需要理解渲染原理、性能路径和扩展边界的读者。初始化与卸载的调用顺序见 [Graph 生命周期](/docs/concepts/graph-lifecycle)。

## 架构分层

<ArchitectureDiagram locale="zh" />

业务通过包根的 `Graph` 和扩展契约使用 G6Lite。Graph 编排数据转换、布局和运行时；DataModel 管理图数据与状态；RenderScheduler 根据变化范围协调绘制。Renderer、Picking 和 GPU Buffer 属于内部实现。

各层围绕同一份图运行时协作：布局提供坐标，交互产生数据或状态变更，调度器将变更交给对应图层。职责分离使布局算法、信息层和交互能力可以独立扩展。

## 绘制图层

G6Lite 使用 WebGL 批量绘制节点和边，并用 Canvas 2D 处理文本测量、标签碰撞与分组包围框：

| 图层（从下到上） | 绘制内容 | 选择原因 |
| --- | --- | --- |
| Canvas 2D underlay | Combo 包围框 | 适合分组边界及背景信息 |
| WebGL 主画布 | 节点、边和箭头 | 适合大量同类图元批量绘制与 Buffer 更新 |
| Canvas 2D overlay | 标签、图标与装饰 | 便于文字测量、排版和碰撞处理 |

这些图层共享相机、尺寸、DPR 和调度信号，属于同一个 Graph。WebGL 优先使用 WebGL2，不可用时回退 WebGL1；运行环境限制见[浏览器与运行环境](/docs/compatibility/browser)。

## 渲染与更新路径

### 首次渲染数据流

调用 `render()` 后，Graph 根据配置准备输入、建立运行时并完成首帧：

异步布局返回时，Graph 检查渲染代次和销毁状态，避免过期结果写回。render Promise 表示当前初始化/提交路径完成，不是 GPU 完成计时；插件挂载等边界按[生命周期参考](/docs/api/graph/lifecycle)查询。渲染代次是内部取消与结果提交机制，业务通过公开生命周期方法管理实例即可。

### 高频更新路径

RenderScheduler 根据变更级别选择处理路径：

| 变化 | 主要路径 |
| --- | --- |
| 节点 selected / highlight / inactive | 状态解析与 GPU 样式 patch，必要时重新处理 |
| 边业务字段或状态 | 完整处理，保持边类型、可见性与箭头批次一致 |
| 批量节点位置 | 邻接数据更新、相关 Buffer 区间上传、Canvas 图层重绘 |
| 标签或 Combo 信息 | 对应 Canvas 2D 信息层重绘 |
| 相机平移与缩放 | 更新 uniform 后重新 draw，不重建图数据 Buffer |
| 完整数据替换或结构变化 | 更新 DataModel，完整或部分处理渲染数据与 Buffer |

因此选择、高亮和拖拽应通过状态、位置和批量 API 更新现有实例。业务侧如何选择更新方法见[数据指南](/docs/guides/data)，性能实践见[性能调优](/docs/metrics/performance-tuning)。

## 布局与交互协作

### 布局与 Worker

布局层根据图数据和配置计算坐标，Graph 将结果写入 DataModel，再交给 Renderer。官方算法按 `layout.type` 懒加载；支持的耗时布局可通过 Worker 减少主线程阻塞。

布局取消后，旧计算结果不会写回当前渲染代次。Worker 不会消除算法本身的成本，已有坐标的数据可以省略布局。算法选择、参数和 Worker 限制见[布局配置](/docs/guides/layout)。

### 交互与 Picking

InteractionDispatcher 统一处理指针事件与命中检测，将规范化事件分发给 Behavior：

```text
原生事件 → 命中检测 → 图事件 → Behavior → 公开的数据或状态 API
```

节点和边优先使用 GPU Picking；命中缓冲不可用时回退 CPU 检测。Combo 使用自身的几何命中路径。Picking 缓冲按需维护，无需每次绘制都执行拾取。

交互产生的变更重新进入更新调度路径，Behavior 无需直接操作 framebuffer。使用方式见[交互配置](/docs/guides/interactions)和[事件](/docs/guides/events)。

## 扩展边界

G6Lite 支持 node、edge、label、decoration、layout、behavior、transform 和 plugin 八类扩展。它们分别参与图形描述、信息层绘制、坐标计算、事件响应或运行时编排。

有状态扩展通过 `ExtensionContext` 的 data、state、viewport 和 `requestRender()` 能力协作，不应持有内部 DataModel、Renderer、WebGL context 或 GPU Buffer。

注册方式、实例作用域与清理规则见[扩展体系](/docs/guides/extensions)；公开契约的稳定性见 [API 稳定性](/docs/compatibility/api-stability)。

## 资源归属与释放

| 资源 | 负责方 | 释放时机 |
| --- | --- | --- |
| DOM 容器、业务 fetch 与外部订阅 | 应用 | 页面卸载或请求失效 |
| 图画布、调度、尺寸观察和交互 | Graph | destroy |
| Worker / 布局请求 | 布局运行时 | 完成、取消或销毁 |
| 插件 DOM 与订阅 | 扩展实例 | 扩展 destroy |
| WebGL buffer / framebuffer | 内部渲染器 | 对应运行时销毁/资源恢复 |

这些是实现职责，不是新的业务 API。实例清理见[React](/docs/getting-started/react)、[Vue](/docs/getting-started/vue)，扩展只依赖[公开上下文](/docs/api/extensions/registration)。context lost 恢复受浏览器与设备影响，不承诺业务状态或页面环境自动恢复。
