G6-GL 使用仓库内统一的 Node 与浏览器 Benchmark 运行器验证性能链路。性能结果只在运行环境、数据规模、配置和采样模式一致时具有可比性；官网不使用缺少环境信息的绝对跑分或跨机器营销对比。

本页记录的是测量方法和选型边界，不表示 G6-GL 在所有数据、布局和设备上都快于其他图库。布局、纯渲染和交互更新必须分别比较。

## 运行入口

先安装依赖，然后在仓库根目录执行：

```bash
npm run benchmark -- --suite all --mode quick
```

参数含义：

- `--suite node`：DataModel 与布局微基准。
- `--suite browser`：公开 Graph API、首屏、交互、拾取和内存趋势。
- `--suite all`：依次运行 Node 与浏览器套件。
- `--mode quick`：用于本地和发布链路的快速验收。
- `--mode full`：扩大数据档位与采样量，用于审核基线。

例如：

```bash
npm run benchmark -- --suite node --mode full
npm run benchmark -- --suite browser --mode full
```

命令会先构建 npm 包，再把 JSON 与 Markdown 报告写入 `performance/`。本地原始报告默认不提交；只有经过审核、环境可比的结果才进入 `tests/perf/baselines/`。

## 指标范围

Node 套件覆盖数据模型替换、位置与业务数据更新、状态切换、增删节点、邻居查询和布局计算。浏览器套件覆盖：

- 批量更新节点位置和业务数据直到下一帧完成。
- 批量状态更新、邻居与邻接边查询。
- 首次渲染、布局耗时和不含布局的渲染耗时。
- 拖拽与缩放帧率、P95 帧耗时和掉帧比例。
- 拾取耗时、Highlight 延迟和销毁后的堆内存趋势。

报告中的内存变化是趋势信号，不等同于内存泄漏证明；垃圾回收时机、浏览器进程复用和显卡驱动都会影响结果。

## 环境要求

浏览器套件需要可用的 Chromium/Chrome 与 WebGL 硬件加速。公开或比较结果时至少记录：

- G6-GL 版本、Git commit 与工作区是否干净。
- Node、Chromium、操作系统和架构。
- CPU 型号；浏览器结果还需记录 user agent、视口和 DPR。
- 数据节点/边数量、布局、迭代次数与 quick/full 模式。
- 样本量、RME 与运行器产生的 warning。

Benchmark 报告会自动写入大部分环境字段。不同环境的结果不应直接计算“提升百分比”。

## 当前公开口径

- Quick 模式用于验证运行器、构建产物和关键路径可以完整执行，不作为营销基线。
- 首页只展示 WebGL 1.0、内置布局能力与包体积预算等稳定事实。
- 包体积由 `size-limit` 独立校验，详见 [包体积](/docs/metrics/bundle-size)。
- 具体业务选型应使用真实数据和目标设备运行 full 模式，再结合 [性能调优](/docs/metrics/performance-tuning) 分析瓶颈。

## 常用图库选型对比

以下内容根据各项目公开文档整理，核对日期为 **2026-07-29**。它比较产品定位和能力边界，不是跨项目绝对跑分。

| 方案             | 核心定位与渲染                                                           | 数据与布局                                                                   | 扩展和生态                                                          | 更适合的场景                                                      |
| ---------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------- |
| **G6-GL**        | WebGL 批量绘制节点和边，Canvas 2D 承担标签与 Combo；强调渲染后的增量更新 | 包内提供统一 Graph 数据 API，并接入 AntV Layout                              | 通过包根注册节点、边、行为、布局、转换和插件；当前仍为 `0.1.x` beta | 需要轻量 WebGL、大图高频交互、AntV 布局和受控扩展边界的业务图     |
| **AntV G6 v5**   | 完整图可视化框架，覆盖渲染、布局、分析、交互、动画和组件                 | 内置能力和配置面更完整                                                       | 元素、行为、插件、动画和组件生态更成熟                              | 图规模不是唯一矛盾，且需要完整图可视化能力和生态时                |
| **sigma.js v3**  | 基于 WebGL、面向数千节点和边的图渲染器                                   | 使用 Graphology 作为图数据模型；布局通常由 Graphology 布局包或业务预计算提供 | 自定义 Program 和 Graphology 生态成熟，产品重心更接近高性能图渲染   | 已采用 Graphology，已有坐标或独立布局链路，重点是大图浏览与探索时 |
| **Cytoscape.js** | 图论模型与可选交互渲染器结合，也可在 Node.js 中做图分析                  | 图查询、算法和布局能力丰富                                                   | 扩展数量多，科研、生物网络和通用网络分析生态成熟                    | 同时需要图算法、分析模型、成熟扩展和浏览器交互时                  |

资料来源：[AntV G6](https://g6.antv.antgroup.com/en/manual/introduction/what-is-g6)、[sigma.js](https://github.com/jacomyal/sigma.js#readme)、[Cytoscape.js](https://js.cytoscape.org/#introduction)。

选择时应先列出必须能力，再使用同一份业务数据验证候选方案。例如，sigma.js 使用已有坐标而 G6-GL 重新运行 force 布局时，首屏总耗时不能直接归因于渲染器；应分别记录布局时间和不含布局的渲染时间。

## 如何进行数值对比

- 固定数据、坐标、节点/边样式、标签策略、视口、DPR、浏览器和硬件。
- 预置坐标与重新布局分成两组结果，不能混在同一列。
- 同时记录中位数、P95、样本量和误差，不用一次运行结果得出结论。
- 除首屏外，至少验证拖拽、缩放、拾取、高亮、批量更新和销毁后的内存趋势。
- 将候选库版本、适配代码和完整配置与报告一起留档，避免后续无法复现。

运行器实现与更完整说明位于仓库 `tests/perf/README.md`。
